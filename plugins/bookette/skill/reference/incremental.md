# Incremental runs

When `confirmed/` exists the run is incremental.

## Reading the confirmed digest

Never read `confirmed/summaries.json` whole, in any run. It is the only confirmed record of the ledger — there is no confirmed ledger in the workspace — and it can carry thousands of rows, so read it by query: `node <skill>/dist/scripts/pipeline.js digest <workspace> --id <id>`, or the `pipeline_digest` tool where the run maps the command to one, prints the rows one query names and nothing else, at most 20 with the count of all; `--id <id>` names one item, `--amount <amount>` the rows carrying an amount in any print, `--doc <document>` the rows whose `source_file` names a document, and `--vendor <word>` the rows whose vendor contains a word, case ignored. Each task needs one query, and the ids come from the file that cites them:

- a `ledger_changes` entry's `from` (amount, date, vendor, source_file): `--id` the item it changes — an id the arming answer cites in `answers.json`, or a row `--doc` returns for the arming document;
- a step-5 move's `schedule` and `tied`, a `correct_reading` key in an item's `answer_keys`, and a `line_category_q` re-ask: `--id` each id the answer's `cites` in `answers.json`, or the open question's in `open_questions.json`, names;
- a newer reading of a document the digest already carries, and a `possible_duplicates` candidate whose `matched` carries `source`: `--doc` that document;
- an amount you read from a document with no staged reading: `--amount` that amount;
- a corrected 1099's original, booked under its own file: `--vendor` a word of the payer's name (`reference/situations.md`);
- the cross-batch duplicate candidates of the staged readings: no query, step 1 prints them;
- the next ledger id and every total: no query, `pipeline build` assigns the ids and computes the totals.

A staged `waiting_lines.json` is the person asking to sort those lines ("Sort these out" on the Review screen); step 1 prints its `waiting_lines` count. Read it at step 4, before every other question, with no query, since each line carries the digest's item shape (`id`, `date`, `vendor`, `amount`, `source_file`, `line`), and ask about them as step 4's "Lines the person asked to sort" bullet says.

## The incremental contract

Process only this batch's documents: the files in `inbox/`, plus the readings staged under `extractions/` (the product path stages every not-yet-consumed reading there; the inbox is the eval path's originals). Propose only additions in `out/ledger.json` without ids — the assignment step numbers them past the highest id in both `items` and `held` (`L0001`-style) — and changes to confirmed items in `out/ledger_changes.json`, one entry per change: `{"id", "field", "from", "to", "answer_key?", "source_file?"}`. Each `to` is the plain value, never an option effect's `to` object: an `entity` change carries the entity key (`"to": "ent_1"`), and a `line` change the schedule line as a string (`"to": "8"`), with a tag in a `tag` change of its own, and a `settled` change carries `"to": true`. `from` must carry the confirmed value for amount, date, vendor and source_file, and is optional for line, tag, meal, entity, trip and settled; `schedule` is not a changeable field, because a row's schedule follows its entity; every entry must be armed by an `answer_key` whose `answers.json` entry cites the changed item and whose chosen option's `ledger` effect covers the changed field (a `category` effect arms `line`/`tag`, an `entity` effect arms `entity`, and also `line` on an item whose `entity` change moves it to an entity on another schedule than its digest `schedule`, a `trip_assignment` effect arms `trip`, a `settled` effect arms `settled` (`to` `true`) — an `effect: none` option arms nothing but a placement's un-place (step 5: an `entity` change to `null` on the lines an `open_` `placement` question cites, after a `personal`, `not_mine` or `per_document` answer), so a `pass_through` answer's `own_income` arms its cited lines' `entity` and crossing `line`, its `inside` arms their `settled` change, and nothing else, a batch document or another answer included, arms a change of any field on a line a `pass_through` question asks about or answered), or by a `source_file` naming a document of this batch: a file in `inbox/`, or a reading staged under `extractions/` by basename or basename without its extension. Every change to one item that names a source document (an arming inbox `source_file`, or the `to` of a `source_file` change, where `null` names none) must name the same one, spelled with the same string; a change armed only by an `answer_key` names none and conflicts with nothing. Split changes are refused. `held` lists the earlier items that are not confirmed (flagged, held for review, or unclassified): they are not confirmed facts, take no `ledger_changes` and are left out of `totals`, and their ids are never re-used. A cross-batch duplicate is a candidate step 1 names in `possible_duplicates`: a staged reading's page or transaction whose amount equals a digest row's in `items` or `held`, on the same day (`matched` carries `date`) or within three days of it (a card posts a purchase a few days after the receipt), with the vendor on both sides shown for your judgment — advisory, because a receipt and a card export spell one vendor two ways. Judge each candidate from the reading and flag a restatement instead of booking it twice (`near_duplicate_of` in `out/documents.json`, and a `near_duplicate` finding naming both documents); a candidate that is a different transaction books as usual. A candidate whose `matched` carries `source` is a digest row whose `source_file` names the staged document itself: the digest already carries that document, so it feeds the disagreement and `correct_reading` rules below and is never a second booking. The verdict prints the first few candidates per document and the count; the full list is `out/inventory.json`'s `possible_duplicates`. A document with no staged reading (the eval corpus's originals) gets no candidate: for one, look up each amount you read with `pipeline.js digest <workspace> --amount <amount>` and judge the rows it returns. The digest carries each item's `line`, so step 4 can tell a travel line (Schedule C line 24a), a folio's or a ticket's asked only carrying its trip, and a line choice is still never re-litigated, since only an answer or a batch document arms a `line` change; it carries each item's `schedule` and whether the item is `tied`, which step 5 uses for a move. The digest is the booked fact: when a newer reading for a document a confirmed item already carries disagrees with the confirmed values (vendor, date or amount), record a finding naming the document, the confirmed item it disagrees with and which of vendor, date or amount differs — a vendor or a date may be named, an amount never, because the confirmed amount is on the cited line — never book a second item for a source the digest already carries, and never silently adopt the newer values. That newer reading is of the document the confirmed line itself cites (the digest row's `source_file` names it; step 1's candidate whose `matched` carries `source`), so the disagreement is a finding, never a change and never a second line, and `check_outputs.js` refuses a vendor, date or amount change armed by the changed line's own document. A different document of this batch that supersedes the line's document — a form marked CORRECTED from the same payer (`reference/situations.md`) — is not a disagreement: it arms a `ledger_changes` entry on the confirmed line by its own `source_file`, with a `note` finding, and the original's document is never booked again. A confirmed value changes only through a `ledger_changes` entry a person's answer arms or a superseding document of this batch arms by its `source_file`, never through a re-read of the line's own document; no question you ask can carry a value correction — an option you write names a category, an entity, a trip or a register input, never a ledger line's amount, date or vendor — so the disagreement is a finding, not a question. The one exception is a correction the person made: when `answers.json` carries a key beginning `correct_reading:doc_<id>`, book no second item for a line that key's `cites` names, whatever its vendor, date or amount now read, and write no `ledger_changes` entry for that line's vendor, date or amount — Bookette applies the person's values to the cited line at import where the line took the old reading's value, and `check_outputs.js` refuses an entry under the key or for those fields of that line; for a cited item whose `answer_keys` lack that key, a field where the newer reading equals the effect's `to` is not a disagreement. A line the key does not cite, and a transaction a newer reading finds that no digest line carries, is booked as usual. Once a cited item's `answer_keys` carry that key, the correction has applied, and a newer reading whose vendor, date or amount differs from the item is a disagreement as above, so record the finding. Reuse a confirmed web value instead of re-fetching: silence is reuse, and you need not re-emit a confirmed value in `out/web_values.json`. The confirmed tax payments need no re-emitting: silence keeps every stored payment, so leave `out/tax_payments.json` absent unless this batch's documents stage a payment or settle a change to one. A written `out/tax_payments.json` is the complete set the build computes from, so carry every confirmed payment in it unchanged unless a change is settled; `check_outputs.js` refuses a confirmed payment a written file drops unless a ledger line now cites its payment evidence (`payment_source`), and refuses silence while a ledger line cites a confirmed payment's payment evidence or bill, which the kept payment would record twice. A line citing a staged payment's bill is removed, never the payment. The confirmed home costs and the entity's `home_office` areas need no re-emitting: silence keeps every stored cost and the stored areas, so leave `out/home_costs.json` absent and the entity's `home_office` key out unless this batch's documents settle a change, and to clear the areas write both keys as `null`. A written `out/home_costs.json` is the complete set, which replaces every stored cost, so write it only to add, correct or remove a cost, carrying the rest; a document feeds the ledger or the home costs, never both, so a confirmed cost whose document a ledger line now cites must leave through a written file, and `check_outputs.js` refuses a confirmed cost that a written file drops any other way. `out/documents.json` covers this batch only — the inbox files and the staged extraction documents alike.

## A batch with no new document

An event can stage an empty `inbox/` and no reading under `extractions/`: it carries only an answer, a declared or edited place, changed notes, or the person's request to sort the waiting lines. The run is the same run over the confirmed state. A staged `waiting_lines.json` makes it no empty batch: step 4 asks about its lines, and `check_outputs.js` refuses a run whose questions cite none of them (a document cited without its lines cites every line booked from it), unless each is tied to a trip or vehicle, or is a travel line no trip ties, and an `entity_unestablished` finding cites each. Step 1 prints no document. Write `out/documents.json` and `out/ledger.json` as empty lists (`[]`): `pipeline build` stops at its first stage without the ledger, and the step-8 check names a missing `documents.json`. Apply what changed: the `ledger_changes` entries the answers arm (step 5), `out/profile.resolved.json` (always), and the questions a declared place or an answer leaves open (step 4); the confirmed tax payments stay in silence, as above. Write `out/findings.json` with what is newly open, `[]` when nothing is, and run `pipeline build` until its verdict passes. A batch with nothing to apply ends the same way: empty lists, the profile carried forward, no finding of its own, and a build that passes — an empty batch is not itself a finding. The carried state can still require one: when the verdict names a finding the carried profile or payments call for (a `missing_receipt` for a home office with no regular reading, a `method_comparison` for one with both readings, an `entity_unestablished` for a payment whose parcel no entity claims), write it.
