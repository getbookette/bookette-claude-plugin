# 4. Ask questions instead of guessing

Write `out/questions.json`, a list of question objects that the app renders as question boxes:

```json
{
  "key": "unassigned_line_entity_q",
  "prompt": "Which property were the Home Depot receipts of March 3 for?",
  "help": "The receipts print no address, so Bookette can't tell which property the supplies went to; your accountant keeps each property's costs apart.",
  "options": [
    {
      "id": "birch",
      "label": "2207 Birch St",
      "effect": {
        "kind": "ledger",
        "field": "entity",
        "from": null,
        "to": { "type": "entity", "entityKey": "birch", "entityName": "2207 Birch St" }
      }
    },
    {
      "id": "cedar",
      "label": "Cedar Cabin",
      "effect": {
        "kind": "ledger",
        "field": "entity",
        "from": null,
        "to": { "type": "entity", "entityKey": "cedar", "entityName": "Cedar Cabin" }
      }
    }
  ],
  "allow_free_text": false,
  "cites": ["L0009", "L0010", "inbox/home_depot_receipts_march.pdf"],
  "blocking": false
}
```

- **Ask about anything the documents and `profile.json` cannot settle** — which property or business a line belongs to, whether a purchase was for the business, what was paid for a property and when it was first rented, what work a job involved, how many nights a short-term rental was let and how many days it was used personally — and ask nothing the documents settle: a payout export that lists the stays settles the rental days and the stay count, so write them into the profile and ask about what it leaves open. A trip the documents place is recorded, never asked (step 5): no question asks where a trip went or what it was for, and its purpose is the person's to add on the Trips screen; a trip no document places, and a travel line no trip ties, are asked which place they were for (the Trips no document places paragraph). Ask for facts, never for a treatment (rule 4): "what work was done", not "repair or improvement". Every question costs the person a click: a run asks at most 15, so ask the ones whose answers change the books most and leave the rest for the next run.
- **Found places.** Book every line first (step 3), unassigned when no staged entity takes it; then, before asking about lines one by one, group this batch's unassigned lines by the place the documents point to: a situs or service address several readings share, or the payer of a 1099 or a payout export. A place `profile.json` does not stage is a found place: ask one `register` question for it (the Key recipe paragraph), citing its lines and the documents they came from — only its `confirmed` lines that no trip or vehicle ties: a `flagged` or `unclassified` line, a held row and a trip- or vehicle-tied line are never cited on a found-place question (`check_outputs.js` refuses a register question that cites one) and are left for a later run — with one `entity_register` option whose `entityName` is the place as the documents spell it (the street number and street name for an address, so a tax bill's situs matches it later; the name a payout statement prints for the place, else its listing; the payer's name for a business's income) and carrying what those documents print as the place, so a rental found by an address writes that `address` as the documents print it, the whole situs or service line, and a rental found by a payout statement writes the `listing`, the platform and the id exactly as the statement prints it, in place of the address; when a cited document prints an address, write the address (the property is known by it, and a later statement's listing is recorded by the rental options below), and write the listing only for a rental whose cited documents print none. A rental's register option carries exactly one of the two and a business's neither, and its address or listing is no place `profile.json` already carries (`check_outputs.js` refuses another shape, `register_placement`, a listing that fails the rules a listing on a `ledger`/`entity` option passes below, and an address or listing a staged place carries), a `ledger`/`entity` option for each staged entity it could be instead (within the four-option limit, but a found rental's question offers every staged rental), and a `none` option whose `id` is `not_mine`. The prompt and the labels state what the documents show — "an address on Lakeview Rd, on 2 cleaning receipts" — never a treatment word. One question per found place and one found place per question; a place the documents point to that `profile.json` already carries by name, alias, address or listing is not found, so book its lines there (this run's own lines; lines already confirmed and unassigned wait for the Key recipe paragraph's re-ask). A found place that may be a place `profile.json` stages is still asked, with that place's `ledger`/`entity` option first: an address the documents print where a staged rental carries none, a payout platform the documents or a staged rental's note say it is let through, or a property manager a staged rental's policy or note names. On an address match write the address on that option's `to` value as the documents print it — `{"type":"entity","entityKey":"ent_2","entityName":"Birch Cottage","address":"88 Fern Hollow, Bend"}` — so confirming records it on the place; write an address on no other option, and never for a place that carries one. A payout statement printing a listing no staged rental carries — the platform and the listing or property id a statement prints — that a staged rental's note or the documents point to (the note says the rental is let through that platform, or the statement prints the rental's name or address) is asked with that rental's `ledger`/`entity` option first, recommended, carrying the listing on its `to` value: the platform as the statement or the note names it and the id exactly as the statement prints it — `{"type":"entity","entityKey":"ent_2","entityName":"Cedar Cabin","listing":"Vrbo 4820193"}` — so confirming records it on the rental and its later statements book there with no question (step 3). When the question's `entity_register` option carries a `listing`, every `ledger`/`entity` option naming a staged rental carries that same listing on its `to` value, not only the pointed rental's, so whichever rental the person picks records it and the next statement books there with no question; `check_outputs.js` refuses a rental option of such a question that carries no listing or another one. The pointed rental's option is still first and recommended; with none pointed, the `entity_register` option is. On every other question the listing rides only the option that books the lines to the rental the documents point to. When the printed id runs to nine or more digits, write no `listing` on the option, because a question refuses a run that long; the rental's option still goes first and recommended, and the person records the listing on Account. Only when the printed id runs to nine or more digits and nothing else points to the place does the question change shape: ask a `placement` question (a `ledger`/`entity` option per staged rental, a `none` option with `id` `personal`) when at least one rental is staged, and otherwise ask nothing and leave the lines under an `entity_unestablished` finding; write no `entity_register` option, since its listing could not be written. A payout-found rental whose printed id is shorter is always asked as a `register` question whose `entity_register` option carries that listing, as above. The person records the listing on Account. An option records one of an address, an alias and a listing: when a statement prints both a listing and an address, write the listing; the address match serves documents that print no listing. Write a listing on no option but those, never one a staged place carries, never for a place that is not a rental, and only one a document the question cites prints. A found rental's question — its `entity_register` option a `RENTAL` — offers every rental `profile.json` stages, each as its `ledger`/`entity` option beside the register option, however many there are, so the person can say which rental it is; when no rental's note or documents point to it, recommend the `entity_register` option. A found business may be a staged business under another name — a 1099's recipient or a deposit's account holder no staged business carries by name or alias: offer that business's `ledger`/`entity` option first, recommended, only when the documents point at it — the found name's 1099 is paid by a payer the business's `payers` lists, or its documents print the address or EIN the business's own documents or `profile.json` carry — never on a likeness of work or name alone, and write the found name as the documents print it on that option's `to` value as `alias` — `{"type":"entity","entityKey":"ent_3","entityName":"Northpeak Consulting","alias":"Peak Studio"}` — so confirming records it as another name the business goes by. Word it as a fact about the name ("Peak Studio is another name for Northpeak Consulting"), never as joining two businesses; write an alias on no other option, never one the business already goes by, and never for a place that is not a business. Mark the most likely option of every found-place question `"recommended": true` and put it first: the matching staged place's option when one matches, else the `entity_register` option. The Review card pre-selects it and the person changes it or confirms. Only a `register` question and a `placement` question (the Recommended placements paragraph) mark an option recommended, and only one (`check_outputs.js` refuses a recommended option that is not first, a second one, one on another question, an address or a listing anywhere else, two of an address, an alias and a listing on one option, and a found rental's question that leaves a staged rental out). The lines a found-place question cites are not among the groups the next paragraph chooses between. Lines no place accounts for are asked as one `placement` question per group, with a `ledger`/`entity` option per staged entity, a `none` option with `id` `personal`, and, when the lines come from several documents, a `none` option with `id` `per_document` — never under `unassigned_line_entity_q`, whose catalog entry takes only `ledger`/`entity` options (`check_outputs.js` refuses a `none` there), and so always under an `open_` key on a first run, when no entity is staged; a `per_document` answer means the next run asks about each of those documents as its own `placement` question. Lines an answer of `not_mine` or `personal` cites stay unassigned — a `none` answer moves nothing, so write no change for them — and are never asked about again (`answers.json` carries the answer and the lines it cites). A found short-term rental is offered as `RENTAL`, never `STR_RENTAL` (the Effects rule below: an `entity_register` option never takes the `STR_RENTAL` kind), with the rental facts in the prompt and a `fair_rental_days` finding for the accountant. When a found place's documents show a trip (a ticket, a hotel stay, or receipts on days away from the travel home), every option that places its lines — the `entity_register` option and each `ledger`/`entity` option for a staged entity — carries the trip in `trips` (the Effects paragraph) rather than the profile: its lines stay unassigned and untied, the question cites them, and the trip lands under the place the person picks in the run that applies the confirmation (step 5); the recommended option, a matching staged place's `ledger`/`entity` option included, carries the same trips, so confirming the pre-selected place records them under it. A stop abroad that ends within a week before such a trip begins, with no line between them booked from a document printing the home's city, is a segment of that one trip (step 3: one itinerary is one trip): carry the whole itinerary, a segment per city, and cite the stop's lines on the same question. The Review screen draws the found-place questions together on one card and the person confirms them in one update, so word each prompt to stand on its own.
- **Lines the person asked to sort.** A staged `waiting_lines.json` (the confirmed lines no place holds, none settled and no open question cites, each `{"id", "date", "vendor", "amount", "source_file", "line"}` as the digest prints it) is the person's "Sort these out" on the Review screen, so ask about its lines before every other question of the run, except a line an answered question about its place cites — `unassigned_line_entity_q`, a `placement`, `register` or `pass_through` question, never a `line_category_q`, a correction or another fact, which place nothing — since it is owed no question here (a `pass_through` answer's lines the run settles or moves as that answer says, step 5): first the ones a note in `notes.json` places — a place's note, or the year's note naming a place, that names their vendor, day or document — one question per place citing them, with that place's `ledger`/`entity` option first and a prompt saying the person's note names it, because a confirmed line moves only on an answer and never on a note alone (`reference/incremental.md`); then the rest, grouped as the Found places paragraph groups lines; then this batch's own questions, all within the 15, any lines left over waiting for a later run; the file never holds a travel line (Schedule C line 24a) or a line a trip or vehicle ties: a tied line moves only with its trip, and the run that booked a travel line owed it a question then (the Trips no document places paragraph).
- **Keys.** A catalog key (`rules/question_catalog.json` `entries`) is used exactly as its entry and the rules below say, and never otherwise: `line_category_q` whenever its rules call for it, `unassigned_line_entity_q` only as this paragraph says, and every other entry whenever it covers the fact. Which property or business this batch's unassigned ledger lines belong to is asked with `unassigned_line_entity_q` when `answers.json` holds no answer for that key and the lines are one group — booked from one document, or one vendor's lines of one kind, so that one property or business takes them all — citing every one of them. A line a `pass_through` question asks about, or an answered one cited, is never among them: no other question cites it. Its catalog entry takes only `ledger`/`entity` options, so a group that needs a `none` option — `personal`, `per_document`, or a first run with no staged entity to offer — is asked under an `open_` key instead (the Found places paragraph above). When they fall into groups that may belong to different properties or businesses, when the key is already answered (`check_outputs.js` refuses it asked again), or for step 5's follow-up to a typed answer, ask each group as its own `placement` question (the Key recipe paragraph) with a `ledger`/`entity` option per choice, and then no question of this batch uses `unassigned_line_entity_q`. When `open_questions.json` already asks which property or business some lines belong to — under `unassigned_line_entity_q` or an `open_` key — that question keeps its key and the lines it cites: lines of the same group are added by re-asking it under that key, never under another, and only the groups no staged question covers are counted when you choose between `unassigned_line_entity_q` and `open_` keys above. Every other question is your own: write its `fact` and leave its `open_` key to `pipeline.js build` (the Key recipe paragraph) — `open_2207_birch_st_register`, `open_birch_purchase` — so a later run asking about the same unsettled fact gets the same key and finds the person's answer under it. Before you choose a key, catalog or your own, read `open_questions.json`: a fact a question there already asks is asked again only under that exact key, never another spelling. A re-ask replaces the earlier question whole — prompt, options and cites — so word it for what you now know and cite everything it is about, the earlier cites included where they still apply. Re-ask it only when this batch changes what the question covers (a new document about the fact, a line it should also cover); otherwise write nothing for it and it stays open as asked. A later run's evidence that seems to answer an open question does not answer it — only the person's choice does: when a new document changes what an open question should ask (the card charge whose invoice has now arrived), re-ask it under its key folding the evidence in, so the person confirms; never treat the question as answered by the documents, and never tell the person to ignore it. A re-ask's new cites name the documents now and the line ids this run's first build assigned; the re-ask happens even when a line it would cite is cited by another open question — give the shared line to the one question the documents better point to, never to both (`check_outputs.js` refuses a line cited by two), and still write the re-ask. Write no `kind`; Bookette derives it from the key. Check `answers.json` first: an answered `open_` key is never asked again (`check_outputs.js` refuses it); when the answer leaves something open, ask the follow-up as a question of the same fact: the build keys it with `_2` appended (`_3` once `_2` is answered, and so on). A catalog key is re-asked only as its entry's rules say: never re-ask an answered key, with one exception — ask `line_category_q` again for a deferred move (step 5) when every item its staged answer cites already carries `line_category_q` in its digest `answer_keys`, because that answer is then fully applied and the new question supersedes it without losing anything.
- **Key recipe.** For a question of your own write `"fact"`, one of the fact kinds below (`rules/question_catalog.json` `open.facts`), and no `key`: `pipeline.js build` spells the key, `open_<subject>_<fact>` in lowercase snake_case, the whole key at most 64 characters, from the question's cites and options and the profile, numbers a follow-up to an answered key (`_2`, then `_3`), writes it into `out/questions.json` and drops `fact`; `check_outputs.js` refuses a key that is not the one it spells. A question `open_questions.json` stages is re-asked under its staged `key`, written as staged — except three, which are not asked again, and a fourth asked in another shape (the Re-asked found places bullet below). A staged question placing a trip's lines is re-asked with the options, order and recommendation a fresh ask of them takes (the Trips no document places bullet), never the staged order. A question about a trip is not, because step 5 records the trip. A `pass_through` question is not, because only the run that books its export can ask it (the Pass-through column paragraph). A placement question about lines no pointer ties to a place is not, because no question asks about them (the No pointer, no placement bullet). For an entity fact write the profile key it is about in `"about"` (`"about": "ent_2"`, or `"about": "cedar"` for a bare key, exactly as `profile.json` spells it), and for a `miles` fact the key of the vehicle's use it is about (`"about": "use_7"`, from the vehicle's `uses`); leave every `entity_register` option's `entityKey` to the build too, which spells it from the `entityName`. One question per fact: a fact with two unknowns, such as what was paid for a property and when it was first rented, is one question of its kind, never two; no line is cited by two of the `register` and `placement` questions and `unassigned_line_entity_q`, and a document cited without its lines counts as citing every line booked from it. Lodging and travel away from home that a document places is a trip the run records, its lines tied to it (step 5); one no document places is a `placement` question carrying the trip in each placing option's effect (the Trips no document places paragraph). A document whose lines belong to several groups, such as a card export with Home Depot and Office Depot lines, takes one `placement` question per group, each citing its group's lines; the build spells the vendor into each key. An `entity_register` option rides only a `register` question. The fact kinds, each with what its subject is:
  - `register` (place) — a found place (the Found places paragraph) — `open_2207_birch_st_register`.
  - `placement` (document) — which property or business a group of lines belongs to, or whether it is personal — `open_birch_repair_invoice_placement`.
  - `category` (document) — what a document's lines were for, when no catalog key asks it — `open_img_2041_category`.
  - `work` (document) — what work a job involved — `open_birch_repair_invoice_work`.
  - `asset` (document) — an equipment or improvement purchase a document shows — `open_bluefin_invoice_asset`.
  - `purchase` (entity) — what was paid for a property or business the profile carries and when it was first rented or used — `open_birch_purchase`.
  - `rental_days` (entity) — how many nights a short-term rental was let, and the stay count — `open_cedar_rental_days`.
  - `personal_use` (entity) — how many days a property was used personally — `open_cedar_personal_use`; its help in the person's words: "Personal use counts the nights you, family or friends stayed without paying full rent; your accountant uses it to split the cabin's costs."
  - `services` (entity) — the services provided to a short-term rental's guests — `open_cedar_services`; its help: "Services are what guests got beyond the stay itself, such as meals, tours or daily cleaning; your accountant asks about them for a short-term rental."
  - `home_office` (entity) — the home office's areas — `open_northpeak_home_office`.
  - `miles` (use) — the miles a place drove a vehicle — `open_use_7_miles`.
  - `pass_through` (document) — whether a pass-through column of a payout export read by hand sits inside the income column booked as its gross (step 3) — `open_cedar_host_payouts_2026h1_pass_through`.
- **Effects.** An option's `effect` is one the catalog allows: for a catalog key its entry's list; for an `open_` key the catalog's `open.effects` — `none`, `ledger` (`category`, `entity` or `trip_assignment`, and `settled` on a `pass_through` question's `inside` option alone), `asset_register` and `entity_register`; never `trip_register`, which is the Trips screen's. Never a kind the catalog does not list. A `ledger` effect is `{"kind": "ledger", "field": <field>, "from": <value or null>, "to": <value>}`, its `field` the `to` value's `type`, and `from` always written: the same shape as `to`, or `null`. The `to` value is one of four shapes, exactly: `{"type":"category","scheduleLine":"8","tag":null}` (`tag` is `null`, `"REPAIR"` or `"CAPITAL"`), `{"type":"entity","entityKey":"ent_1","entityName":"ACME Corp"}` (the key and the name of an entity in `profile.json`), or `{"type":"trip_assignment","tripClass":"business"}` (or `"rental"`), or `{"type":"settled"}` with `from` `null`; `check_outputs.js` refuses any other shape as untypeable. The two register effects are written exactly as: `{"kind":"entity_register","entityKey":"2207_birch_st","entityName":"2207 Birch St","entityKind":"RENTAL","schedule":"E","ownershipPct":null,"address":"2207 Birch St, Bend, OR 97701"}` (`entityKind` is `RENTAL`, `STR_RENTAL` or `BUSINESS`, `schedule` is `C` or `E`, and `ownershipPct` is a number or `null` and is always written; a `RENTAL` carries exactly one of `address` and `listing`, a non-empty string, as the Found places paragraph says, and a `BUSINESS` neither; a found place whose documents show a trip also carries `"trips":[{"name":"Boulder, Mar","segments":[{"location":"Boulder, CO","start":"2026-03-21","end":"2026-03-22"}],"documents":["inbox/boulder_motel.pdf"]}]`, each trip dated as step 5 dates a recorded one, by documents of this batch, and never a purpose; the same `trips` ride the found place's `ledger`/`entity` options and a `placement` question's (the Trips no document places paragraph), and no other question's options or effects carry them); `{"kind":"asset_register","entityKey":"ent_2","entityName":"2207 Birch St","description":"Purchase of 2207 Birch St","assetKind":"REAL_PROPERTY","costBasisCents":34000000,"landValueCents":6000000,"placedInService":"2021-07-01"}` (`assetKind` is `REAL_PROPERTY`, `EQUIPMENT` or `IMPROVEMENT`; `costBasisCents`, `landValueCents` and `placedInService` are each written only when the answer settles that input, in cents and as an ISO day). A `ledger` question `cites` at least one ledger line; a register question cites the documents the fact came from. An `entity_register` option's `entityKey` is the one `pipeline.js build` spells from its `entityName` (the Key recipe paragraph), never `ent_<n>`, which names a declared row (`check_outputs.js` refuses either otherwise). An `entity_register` option never registers a short-term rental, never names an entity the profile already carries as one, never moves an entity to another schedule, and a question's `entity_register` options never differ in schedule: Schedule E or C for a short-term rental is the accountant's call (rule 4) — record the facts and write a `fair_rental_days` finding.
- **Re-asked found places.** A `register` question whose place `profile.json` now carries by the same name, alias, listing or address, because the person has declared it since, is re-asked under its staged key as a placement, citing the lines the staged entry cites: that place's `ledger`/`entity` option first and `"recommended": true`, carrying no listing or address on its `to` (the place already carries it), then every other staged rental's option when the place is a rental, no `entity_register` option, and the `not_mine` option; its lines are confirmed and unassigned, and they move only on the person's confirm (`check_outputs.js` refuses a register option naming a place `profile.json` carries, and a re-ask whose first option is not a recommended `ledger`/`entity` option onto the staged place that carries it by the name, alias, listing or address its key spells, that leaves a staged rental out of a rental's question, or that drops a line the staged entry cites; a business is re-asked with the business first and the staged rentals need not be offered, and a run that neither re-asks nor answers a staged `register` question whose cited lines are still unassigned is refused, `staged_register_dropped`).
- **Facts no effect can carry.** Rental days, personal-use days, the stay count, the services provided, the home office's areas and the miles a place drove a vehicle have no effect kind, so a question about one is asked with `allow_free_text: true` and options of `none`: the person's words reach the accountant on the report, and you write the `fair_rental_days`, `personal_use` or `missing_receipt` finding the facts call for. Never write those profile fields from an answer's words (step 5). A fact a `profile_fact:` key records is settled: ask nothing about it. A run that books a staged short-term rental's documents always asks its `personal_use` and `services` facts, each under the key the Key recipe paragraph spells from the rental's key (`open_cedar_personal_use`), and never leaves them for a later run. The only exceptions: `profile.json` records the fact (`personal_use_days`, `services_note`), or `answers.json` holds an answer to the fact's question under any of its keys (`open_cedar_personal_use` or a follow-up such as `open_cedar_personal_use_2`). Count them and the `pass_through` questions against the 15 first; the questions about the lines the person asked to sort use what is left, and "before every other question" is their order in `out/questions.json`, not their budget.
- **A purchase.** A `purchase` question's option that writes a property's `costBasisCents` (an `asset_register` effect whose `assetKind` is `REAL_PROPERTY`) also writes its `landValueCents`: the land allocation the closing statement prints, else the land value the property's tax bill prints (the assessor's land figure, which a staged reading of the bill carries as `fields.other.land_value`; with several bills for the property, the latest), copied as printed — never a share, a ratio or a figure you work out, and never above the basis (`check_outputs.js` refuses that effect as untypeable). A condominium's bill that prints a land figure is no exception. The question cites the document the land value came from beside the one the basis came from, and the label names both ("The gross amount on the 2019 closing statement and the land value on the Denver tax bill"). The basis a closing statement gives is the total its staged reading carries, the gross amount due from the borrower: `check_outputs.js` refuses a purchase option whose `costBasisCents` is not the staged total of a closing statement its question cites, unless the person typed that figure (`purchase_basis_reading`). When no document you read prints a land value for the property, write the option without one, say so in its label ("No document shows a land value"), and write a `note` finding citing each of the property's tax bills, or the purchase's documents when there is none, that no document shows the land value, so the accountant settles it. `check_outputs.js` refuses a purchase option that writes a basis and no land value while this batch carries a `property_tax_bill` of that property — one the question cites, one stating a parcel the property's `parcels` list, or one printing its address — and no `note` finding cites that bill, or a note cites it but its staged reading carries `fields.other.land_value` and none of the property's bills stages one above the basis (`purchase_land_value`). A land value above the basis no option can carry: write the option without one, say so in its label ("The land value on the Denver tax bill is above the price paid"), and write a `note` finding citing the bill that its land value is above the price paid, so the accountant settles it.
- **Recommended placements.** A `placement` question marks its first option `"recommended": true`, a `ledger`/`entity` option onto a staged place, only when the run can cite one of two pointers to that place, or one of the Trips no document places paragraph's, and otherwise marks none. The recommended option carries its `pointer` when the No pointer, no placement bullet's quote is what points to its place. The option for the place a pointer names is listed first in `options`, whatever order `profile.json` stages the places in. The only staged business: lines whose vendor sells software, office supplies, fuel or equipment, or a 1099-NEC made out to the person with no business name, when exactly one business is staged and no rental's documents or notes name the vendor. A rent stream left to one rental: one payer's deposits in at least nine distinct months on a checking export that names no property for them, when another row of that export books rent to a staged rental by its name or unit, every other staged rental books rent in this run from a document, and exactly one staged rental books no income from any document; recommend that rental and write one `note` finding naming the export, the payer and the elimination, citing the stream's lines beside the export. The export's other unnamed rows are asked as their own groups, as above, since they can belong to different places. A recommendation is never `placed`, in either review mode: its lines stay unassigned, the Review card pre-selects it, and they move only on the person's confirm. It is judged again on every run until the key is answered, and the key does not carry it — the build spells a placement key from the fact, the cites and the vendor, never from the option order or the flag — so a re-ask may change or drop it; once answered, the key is answered for the year. `check_outputs.js` refuses a recommended placement option that is not first, a second one, one that books the lines to no place, and one that is also `placed`.
- **No pointer, no placement.** A placement question is for lines at least one pointer ties to a staged place.
