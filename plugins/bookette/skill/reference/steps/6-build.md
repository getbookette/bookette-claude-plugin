# 6. Assign the ledger ids and build the books

Run `node <skill>/dist/scripts/pipeline.js build <workspace>`. It runs three stages in order and stops at the first that fails, printing one verdict: the stage reached, the build's checks, how many entries the build listed outside the tax year (`outside_year`) and the step-8 problems. First it assigns the code-owned ids to `out/ledger.json` from each item's facts, continuing past the confirmed and held ids, and rewrites any `cites` or `applies_to` id you wrote earlier to the assigned one. Never write or edit an `id` yourself, and run `pipeline build` again if you later add or change a ledger item, before anything cites one.

Write the outputs in the order that needs the fewest builds: the step-2 and step-3 outputs first — `out/documents.json`, `out/ledger.json`, `out/profile.resolved.json`, and `out/donations.json`, `out/home_costs.json` or `out/tax_payments.json` when step 3 calls for them — with `out/questions.json` and `out/findings.json` beside them, and the questions and findings that cite a ledger id written after the first build, citing ids read back from `out/ledger.json`: an id is citable only once a build assigns it, so never a placeholder, never an id you have not read back, and writing the citing set after the first build, in one response, avoids the patch cycle a pre-build copy invites. The build rewrites every `out/` file it touches into its canonical shape — keys spelled its way, JSON re-serialized — so a copy you hold from before a build is stale after it: re-read an `out/` file after every build before you edit it, and read back only the file a verdict names.

Before the first build of a run, check: no money figure in any finding message, question prompt or label; every prompt at most 300 characters; every `tax_payments` entry a distinct `payment_source`; every payment whose parcel no entity claims carries an `entity_unestablished` finding; every trip has a purpose or a `trip_purpose_not_stated` finding citing `trip:<key>`; every `purpose_suggestions` entry cites in `document` one of its trip's own `documents` whose reading names the activity or the counterparty, at most two per trip and none on a trip with a purpose but the one event's whose name it carries; no ledger item cites a staged payment's `payment_source` or `bill_source`, nor a confirmed payment's that `out/tax_payments.json`'s absence keeps; no line cited by two questions; and no forbidden word even where a form prints it — transcribe a form's box number and code, never its label (`Box 13, code W`, not the box's own name).

Then it builds the books. The build reads `out/profile.resolved.json` (or `profile.json`), `out/ledger.json`, `out/donations.json`, `answers.json` and — when the workspace stages them — `out/tax_payments.json` and `out/home_costs.json` (`confirmed/tax_payments.json` and `confirmed/home_costs.json` while the run's own file is absent), converts currencies, sums by entity and line — a line, a staged property-tax payment or a home cost dated outside the tax year is listed in `outside_year`, a line with the place and line it would have taken, never converted and counted in no total or comparison — computes the depreciation register, the trip meal comparison, the vehicle method comparison, the improvement-or-repair and expensing-or-MACRS comparisons, the rental-day analysis and the home-office readings, runs validation checks, and writes `out/books.json` and `out/books.md`. Last it runs the step-8 check.

The depreciation register books each asset from the inputs you resolve into the profile: class, cost basis, land value, placed-in-service date, `disposed_on` when the property left service, and `prior_accumulated` when an earlier run carried one. The verdict is what you act on: its `actions` list, one line per row, carries every row of `out/books.json` you must write a finding, a question or a lookup for, with the ids and figures you need. Act on the rows the build prints; never read `out/books.json` back. The rows, and what the books hold:

- A `missing_rules_data` row is a depreciation row with `"computed": false`: it has no rule for its class (its `reason`) — the asset is listed with its inputs and nothing is booked for it. Write a `findings.json` finding with kind `missing_rules_data` naming the asset.
- A `prior_accumulated_mismatch` row means the recorded carryforward (`recorded_cents`) disagrees with the schedule's own accumulation (`schedule_cents`), and the books keep the schedule's figure. Never pick between them — write a finding with kind `prior_accumulated_mismatch` for the accountant.
- Trip meals appear both ways (actual cost and M&IE per diem, each at the limit percentage) with no choice made; the comparison is for the accountant. A trip on one calendar day has no per-diem side (the rules file's `same_day_note`) and shows its actual meals alone. A `missing_rate` row names a trip's locations with no per-diem rate: look each up as rule 8 says, and when the lookup fails, take the exit the failed-lookup paragraph below names.
- Vehicle methods appear both ways (standard mileage priced from the year's bands, and actual cost from the attributed lines) with no choice made. The standard rate's exclusions — the first-year method, depreciation previously taken, five or more vehicles used together — are listed on the row, never applied to either figure.
- The home office appears in `home_office`: the simplified reading from the office area, the regular reading from the home's area and the staged costs dated in the tax year (null when the home's area or costs are missing; a cost dated outside the year is listed in `outside_year` and feeds neither reading), side by side; the build books neither on Schedule C line 30, since the method is the accountant's. Depreciation of the home, the income limit and any carryover are in neither reading. A `missing_receipt` row says the regular reading is missing and what it lacks (`regular_missing`).
- Improvement or repair appears in `improvement_repair`, one row per expense line tagged `capital` or `repair` on a property or business: the line expensed in the year, and the line capitalized as an improvement to the building with its year-one depreciation over the class the entity's buildings agree on (null, with `class` in `missing` when the building's class is not established). Expensing or MACRS appears in `expense_macrs`, one row per `equipment` or `improvement` asset placed in service in the tax year whose class is personal property or not yet established (an improvement with a building's class is the register's): the basis expensed in year one, and its year-one MACRS figure (null, with what is missing, when its class or a rules figure is not on record), with the rules data's de minimis ceilings it passes listed and never applied. The books keep every line where it was recorded; nothing is booked from either reading. Each row prints as a `method_comparison` row, for step 7's findings; an inputs-only depreciation row the expensing comparison carries prints as that comparison's row, not as `missing_rules_data`.
- A short-term rental's day analysis appears in `rental_use`: the day counts, the threshold predicates and the recorded services note, plus the allocations of the operating and of the interest-and-taxes cents by rental days and by the year's length. Nothing is booked from them. Each prints as a `rental_use` row with the day counts and whether a services note is recorded, for step 7's findings.

When the build prints a `method_comparison` row for the home office — the `home_office` row carries both a simplified and a regular reading — write its step-7 finding; no question asks the method (step 4).

A per-diem lookup that fails ends the same way every time. It fails when the fetch is refused or errors, the host cannot be reached (a run with no web access fails every fetch), the page does not state the rate for the location on the trip's dates, or the run's web lookups are spent. Fetch the URL the `lookup` field builds for the city and follow only what it returns — a redirect it names, or the link of the post that matches the location — and when that fails, stop: never retry a URL, never guess another address on the host or try another site, and never fetch past the lookup budget. Record no web value for the key and leave the trip's meal lines as you booked them: the build still books them and their actual-cost reading, leaves the location's days out of the per-diem reading and marks that reading incomplete (`missing <location>` on the report). Write one `missing_rules_data` finding per location, citing `trip:<key>` (step 7), naming the location, the trip and its dates apart from any figure, and saying the official source could not be reached or did not state the rate — `The per diem rate for Osaka, Japan for the trip from 2026-04-18 to 2026-04-19 is not in the rules data, and the official source could not be reached.` — and run `pipeline build` again: the `missing_rate` row keeps printing and the build passes with it. Never use a remembered rate or one from any other source, and never write a per-diem figure yourself. When this session already looked the same location up for the same trip dates and the lookup failed, a later event does not look it up again: write the finding again and fetch nothing. A recorded web value or new rules data for the key, or the person's answer about the trip, reopens the lookup.

If the verdict reports a validation error, fix the ledger or profile and run `pipeline build` again, and act on the rows once the build passes: a failing build's rows can be incomplete. Never edit `books.json` yourself. The check stage names a missing `findings.json` as a missing required output, which is why the first build runs over the `[]` or the findings the core's step 6 has you write with the other outputs; step 7 then adds the findings the verdict calls for. It names a missing `out/summary.json` the same way: step 7 writes it last, so a verdict here whose only problem is the missing summary is this step's pass; go on to step 7.

A `no <currency> rate on <date>` line is one the run's rate snapshot and the rules data both carry no exchange rate for on that day or the seven days before: the vendored Federal Reserve H.10 series cover 2024-12-24 onward, for the currencies `rules/ty<tax_year>/fx/sources.json` lists, and a currency it does not list is the same case. Such a line does not stop the build and needs nothing from you: the build books nothing for it — books.json lists it in `unpriced` with its amount and currency as printed and the place and schedule line it will take, counted in no total, no rate row and no comparison — and the importer flags the line's row itself. Write no finding, mark no document `needs_review`, change no ledger item, and run `pipeline build` again only when the verdict names other work. Never look an exchange rate up and never convert an amount by hand. A web value cannot carry one: the build reads recorded web values only for a trip's per-diem rates (`mie` and `first_last_day`), and the conversion reads only the rules data and the run's rate snapshot, so a rate written to `out/web_values.json` converts nothing.
